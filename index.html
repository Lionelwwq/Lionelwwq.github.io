How I Work

Start at the desk, not the spec

The requirement is almost never the real problem. I watch the task being done first, because the expensive part is usually a step nobody thought to mention.

Safe to run twice

Anything that talks to another system will be re-run — by a retry, a double click, or a person who is not sure it worked. So it is keyed and idempotent by construction rather than by care.

Measure instead of estimate

Every timing bug I have shipped came from a guess that was close enough until it wasn't. Where a real number can be measured, the code measures it.

One place for each rule

Permission checks, tenancy scoping and audit logging live in shared helpers. A rule copied into fifty files is a rule that is already wrong in three of them.

Fail loudly, degrade quietly

A new path should never be able to make the old one worse. New work falls back to the behaviour it replaced, and anything that fails silently gets an alert with a name on it.

Ship it, then carry it

I run what I build: deploys, monitoring, the 3 a.m. version of the problem. Owning the operation is what keeps the design honest.

Amax Leather ERP Platform

The system two furniture companies run their day on — designed, built and operated solo

In plain language: “ERP” is just the name for the software a company runs its whole day on. Amax Leather Canada and Aurora Furniture MFG make and sell furniture, and everything that happens between someone placing an order and a sofa arriving at a home has to be written down somewhere — this platform is that somewhere: one website, one login, where staff take the order, check whether the piece is on the warehouse floor or still on a ship, print the shipping and customs paperwork, and hand the figures to the accounting system so nobody types them a second time. Case Studies

AmaxBot — a GPT assistant that inherits the ERP’s permission model

AI / Node
Situation

The answers to the questions staff asked IT all day — where is this order, do we have stock, what does this account owe — lived in four databases nobody outside IT could query. Every question became an interruption, and the answer came back hours later as a screenshot.

Built

One assistant on two surfaces sharing one accuracy layer: a chat UI with 55 function-calling tools, and a 3,300-line IMAP service that watches a shared mailbox, answers 27 @amaxbot_* email commands, auto-replies from the knowledge base and mails a daily operations digest. Both surfaces answer through the same tools, the same role checks and the same reply audit as the web UI — the email path exists because it reaches the people who never log in at all.

3 engineering decisions, and what I would change
Decision 1

Filter the tool catalog before serialising it, not after. A non-admin’s request is assembled from a list with every write tool already removed — SKU create/update/delete, order writes, price changes, workflow execution — so the model cannot call what was never in its context. That is a stronger guarantee than trusting it to refuse, and it survives a prompt-injection attempt in a forwarded email, because there is nothing to inject toward. The same pass drops rarely-used specialist tools unless the message mentions their subject; the common tools are never droppable, so the gate can cost a niche lookup at worst, never a routine one.

Decision 2

Enforce account scope on tool output, never in the prompt. A dealer- or rep-scoped session runs every tool result through a filter that deletes rows naming an account outside that session’s allowed set before the model sees them, blanks an entire result that belongs to someone else, and logs the removal as a scope violation. Product and stock tools are exempt by name because their rows carry no account at all. The filter is one extracted function rather than a step in the main loop, specifically so the self-repair pass runs it too — an earlier version repaired an answer by calling tools directly and handed back exactly the rows the main loop strips.

Decision 3

Audit the draft reply deterministically, then make the model go and measure. A shared module checks every draft for identifiers the tools never returned, counts that appear nowhere in the tool output, and denials of existence nothing actually verified. A flagged draft is not simply blocked: the specific defect is handed back with instructions to re-check it, because sending the right answer beats withholding the wrong one. Permission refusals are explicitly excluded — “that account is outside the ones assigned to you” is a correct answer that no amount of re-querying will change, and flagging it was burning a model round on most refusals.

Hindsight

The repeat-answer cache. It began as string similarity over previous questions and then grew a rule for every wrong answer it produced: never cache a time-relative question, never cache one containing an order or SKU identifier, never serve a reply whose text looks like an entity card. Every one of those is a guess about the prose after the fact. Cacheability is a property of the tool that produced the answer, so the tool should declare whether its output is live data and the cache should read that flag — instead of pattern-matching the reply and hoping.

Outcome

Staff self-serve from the ERP by chat or by plain email, in English or Chinese, through the same permission model the web UI uses — no second data path that quietly routes around RBAC.

The integration layer — EDI in, accounting out

SOAP / Accounting
Situation

Purchase orders arrived from trading partners over EDI, and the same orders and supplier bills were then re-typed by hand into two separate accounting companies. Every re-key was a chance to transpose a figure, and nobody found those mistakes until month-end close.

Built

Two halves that meet inside the ERP. Inbound: a SOAP client against an EDI provider that pulls purchase orders and returns acknowledgements, advance ship notices and invoices. Outbound: an accounting hub of 6 connectors and 42 APIs on a daily schedule, pushing sales documents and supplier bills into two accounting companies with a per-pipeline sent-ledger and failure alerting behind it.

3 engineering decisions, and what I would change
Decision 1

Store the original document beside the mapped columns. The provider’s pull is a server-side cursor: the first call returns a batch plus a more-records flag, and the continuation call takes no offset — it advances a cursor held in the authenticated session, so the whole cursor has to be drained inside one login or the place is lost. Once a document has been handed over it is no longer “new”, which means a mapping bug found a week later cannot be repaired by pulling it again. So every order and every line is written with its raw payload next to the parsed columns, and the table is uniquely keyed on partner plus PO number so a re-pull updates instead of duplicating. Re-mapping became a local replay rather than a phone call asking a partner to resend.

Decision 2

Make idempotency a soft-flagged ledger, not a delete. Each outbound pipeline keeps a ledger of what it has sent, keyed by order or PO number, and the export query excludes anything currently active in it — so a double-click, a re-run or a retry cannot post the same document twice. A rollback flips the row inactive rather than removing it, which makes the document eligible again while preserving who sent it, when, and in which batch. That distinction is the whole point: a batch the accounting importer rejects has to be un-flagged, or those documents stay marked as sent forever and are never retried.

Decision 3

The importer answers asynchronously by email, so the failure path is an inbox. Imports are accepted and validated later, with the verdict arriving as a message — which makes the integration exactly as reliable as whatever reads that message. The same IMAP service that runs the assistant matches the importer’s failure notices, parses the file name and the per-row success and error counts, un-marks the affected batch so the next scheduled push retries it on its own, and raises an alert naming what will and will not retry. Two guards make it survivable: the block runs ahead of message de-duplication, because every retry notice is a fresh message with its own id, and identical alerts are collapsed to one per cooldown window — a single case-variant SKU once slipped the already-sent check and generated 65 alerts in a day.

Hindsight

Four pipelines grew four near-identical sent-ledger tables and four copies of the mark-and-rollback logic, so every bug found in one had to be re-fixed in the other three. One ledger with a pipeline column and one shared helper would have cost an afternoon and saved all of it. And one pipeline marks documents as sent before dispatch rather than on acknowledgement — which is precisely the failure the alerting then had to be built to catch. Mark on acknowledgement.

Outcome

Partner orders reach the ERP and both accounting companies without re-keying, resends are safe by construction rather than by care, and an import failure surfaces the same day as an alert with the affected rows already re-queued — instead of being discovered at close.

Knowledge-base search — rebuilt as hybrid retrieval

Embeddings / RRF
Situation

The knowledge base behind the assistant was searched with a single MariaDB FULLTEXT match, which only finds literal words — “my couch arrived scratched” never reached the damage-claim article. For Chinese it was not weak, it was dead: FULLTEXT splits on whitespace and Chinese has none, so a whole question arrives as one unmatchable token, and the Chinese title and body columns were not in the index at all.

Built

A retrieval layer that embeds every article once, in chunks, and fuses vector similarity with the existing FULLTEXT query at request time. 26 published articles become 110 chunks; the vectors are 0.64 MB and a full rebuild costs about five hundredths of a cent. Chunk zero of every article is always a card — title, type, tags, summary — because a short question matches that card far better than any window of body text, and body chunks are prefixed with the title so a window never loses its subject. English and Chinese are chunked and embedded as separate documents rather than concatenated.

3 engineering decisions, and what I would change
Decision 1

No vector database. The production MariaDB predates the VECTOR type, and the honest measurement was that the entire index is 0.64 MB. Vectors are stored as raw little-endian Float32 blobs in an ordinary table, loaded into one flat Float32Array for cache locality, and scored with a dot product in Node; per-article scores are max-pooled rather than averaged, so one strongly matching passage carries its article instead of being diluted by the article’s length. A vector service would have been more infrastructure to run, monitor and deploy than the data it holds — even at twenty times this corpus it is roughly 12 MB and a cent to rebuild.

Decision 2

Fuse, never replace — and make the new path incapable of making search worse. Both legs run in parallel and are combined by reciprocal-rank fusion under a cosine floor that discards weak semantic hits as noise; fusion rewards a document both legs like while still letting one excellent list win, which is only safe because the floor keeps junk out of the lists in the first place. Every semantic step is wrapped so a missing key, a rate limit, a timeout, an absent table or a corrupt vector falls straight through to the exact FULLTEXT query that ran before the rewrite, and with the flag off the embedding API is never called at all. One bug that path taught me: both legs are fetched at four times the caller’s limit so fusion has candidates to work with, so the fallback must trim back to the requested limit — without that, a timed-out semantic leg quietly returned twelve loosely-related articles to a caller that asked for three.

Decision 3

Treat cold start as a race, not a wait. The vectors live in the same overseas database as everything else, and loading them on the first question did not reliably fit inside the query deadline, so the first real questions after every deploy were timing out for no good reason. The load is now raced against a short grace period: win it and that question gets the semantic leg; lose it and that one question is answered from FULLTEXT while the load finishes in the background, so every question after it is fast. The loaded index is then revalidated against a cheap stamp query — row count, max id, max timestamp — at most once a minute, because a round trip to that database costs more than the comparison it saves.

Hindsight

Chunk hashes bind model, dimensions, language, position and text, so swapping the embedding model invalidates the affected rows automatically and no migration is ever written — that I would keep exactly. What I would change is the measurement. The head-to-head was eight real staff questions: enough to prove Chinese was broken, nowhere near enough to tune anything. Before I touch the fusion weights or the cosine floor again I would build a proper labelled question set and re-run it on every change, instead of judging by eye.

Outcome

On the recorded run of eight staff questions the old path returned rows for five — and on one of those five the rows were the wrong article, which is worse than returning nothing. The hybrid returned the correct article for all eight, including three Chinese questions that had previously returned nothing at all. It ships behind a flag and degrades to the old query on any failure, so the worst case is the behaviour it replaced.

Social Video Maker — script to vertical video, nothing paid in the chain

FFmpeg / TTS
Situation

Marketing wanted a steady stream of Mandarin short-form video, with no per-video budget and no editor to put in the loop. The requirement was a finished, publishable 1080×1920 file produced from pasted script text in a single pass.

Built

A standalone Node app: text-to-speech narration, b-roll selection, Ken Burns motion, a circle-masked talking-head overlay whose mouth is driven by measured audio amplitude, burned-in captions, FFmpeg assembly, and live progress streamed to the browser. Every service in the chain is a free one — which is not a footnote but the constraint that shapes the design, because free endpoints fail quietly rather than loudly, so the pipeline is built to measure instead of assume.

3 engineering decisions, and what I would change
Decision 1

Build the pauses out of audio, because the engine will not build them out of markup. The free speech endpoint silently returns zero bytes for any SSML containing a <break> tag — no error, just an empty stream — and does the same for inputs past roughly 800 characters. So pacing is constructed the other way round: the script is split at punctuation, each fragment is synthesised as its own call, and cached silence files are spliced between them with the gap chosen by punctuation class — 380 ms after a sentence, 180 ms after a clause, 500 ms at a paragraph, 120 ms at a single line break. That last class exists because treating every visual line as a paragraph put half a second between them, and in a script written one clause per line dead air came to dominate the audio. Fragments are then regrouped up to the size limit to avoid a handshake per clause — but never glued across a sentence break, or the pause they were built for disappears.

Decision 2

Measure the audio; never estimate it. Caption timing was first derived from character counts and it drifted, because digits, punctuation and rare words all take longer to speak than their length implies and the error accumulates until the words on screen are a full sentence behind the voice. Now each synthesised group is probed for its real duration before the audio is concatenated, and that timeline is what the caption builder rides, so the error can never grow past one sentence. Uploaded human narration has no synthesis timeline to use, so there the caption boundaries snap to the nearest detected silence of at least a quarter second — which is exactly where a speaker ends a sentence.

Decision 3

Copy streams when the parameters agree; re-encode only when they do not. Long scripts are split, rendered as segments and merged, and the merge is where the time goes. Each input is probed first, and when codec, resolution, frame rate and sample rate all match, the segments are joined through the concat demuxer with -c copy — a file operation rather than a second full encode. When they disagree it falls back to the concat filter and normalises everything to the project’s standard. The intro-card path deliberately uses the filter even where copying looks possible: the demuxer needs matching streams on both inputs and a still cover has no audio track at all, so the cover is given a silent track and pushed through the filter, rather than shipping a file that plays in some players and not others.

Hindsight

There are two timelines in this pipeline. The captions ride measured audio, but the b-roll cuts are still spaced by character count, and every sync bug I have fixed has been at the seam between the two. The right shape is one timeline object, built once from the measured audio and consumed by captions, cuts and the avatar alike — instead of two estimates that agree right up until they don’t.

Outcome

A publish-ready vertical video from pasted text in one pass, with nothing paid anywhere in the chain, and a 130-case unit suite plus HTTP route tests that boot the app on an ephemeral port. The whole suite runs with no network and no quota, so the parts most likely to break — a free endpoint changing its behaviour under you — are the parts under test.
